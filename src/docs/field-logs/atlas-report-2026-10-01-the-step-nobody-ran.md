## Three — The Step Nobody Ran

The Scaduscope needed two new database tables. Its pull request said so plainly, under a heading that read _Before deploying_, with the exact command an account holder had to run by hand.

Nobody ran it. The zone deployed on 09-26 without its tables, and for about two days every shadowman a visitor tagged was scored only in that visitor's browser and marked _Unrecorded_. Those tags were not stored and cannot be recovered. The shared log said "No names yet from anyone," which was not true. The truth was that the shared record could not be reached.

The repair came in three moves on 09-28:

1. **Diagnose** (#162). Production returned 500 on both Scaduscope endpoints while the sighting endpoint returned 200: the database was reachable, but the tables were missing. The schema moved into numbered migrations, and the offline log now says the shared record is offline.
2. **Generalize** (#166). The single database, named for the JJAMMOCAN sightings, was copied into a new database named `forgotten-industries`, under a runbook that required the two databases' counts to match before the binding moved. The old database is held until 2026-10-28 as the rollback.
3. **Remove the step** (#167). Every deploy now applies pending migrations before it ships, using a token that can edit the database and nothing else. If that step fails, the deploy stops before anything goes live.

The live database records `0000_sightings.sql` and `0001_scaduscope.sql` as applied at 16:43 CT on 09-28.

## Four — The Latch, Late

The sighting intake gate was written on 2026-09-21. It merged at 21:46 CT on 09-30, and the deploy applied its migration, `0002_add_status.sql`, four minutes later. Every submission now enters as `unverified`, and only `confirmed` sightings are shown publicly.

The gate's own commit message says its migration "must be applied to the live database by hand." That was true when it was written. By the time it merged it was not: #167 had landed two days earlier, and nobody needed to do anything. The warning was obsolete on arrival, which is the better failure.

From 09-02 to 09-30, twenty-eight days, the intake accepted and published submissions with no review gate. A read-only query on 2026-10-01 returned **zero rows**. Nobody wrote in. As `FI-LOG-022` put it, that is luck, and it is recorded as luck.

## Archive Meaning

A fix exists in three states: written, merged, and running. Everything in this window sits in the gap between two of them. The Scaduscope's schema was written into a pull request and merged, but never run. The intake gate was written but not merged for nine days. `FI-LOG-022` described the written state as though it were the running one. None of these were failures of knowing what to do. Each was a step that depended on someone remembering to do it, in a window when the someone was unwell.

The repair that matters is not any one fix. It is #167, which takes a person out of the loop: a step that runs itself cannot be forgotten. The operator's own tracker, kept for a different purpose, states the same rule: "A resume with no submission date is a leak, not a blank." The window that began with nothing merged and nothing sent ended with seventeen merges, a shipped gate, and fourteen applications submitted.
